## 功能设计说明书定位和写作说明

系统功能是对设计问题的概括和抽象，描述了系统为了完成预期输出，需要执行的某个任务、动作或活动。
功能域是对不同的功能项进行归纳和组合，对应于功能树上的某层目录。
产品可以按需选择基于某个功能域，对一组归纳和组合后的系统功能进行设计，亦可单独针对某个系统功能进行设计。
本模板描述的是基于功能域的设计方式，针对单个功能项的设计可以直接参考“功能实现设计”章节的要求写作，不需要写作功能域相关的章节。

功能设计说明书定位：
1. 对系统功能进行实现设计，建立系统功能与系统元素（通常是逻辑元素）的关系。
2. 将系统需求（SR）分配到系统元素，形成分配需求（AR）

## 其他shuoming

文档目的是实现 Daft 在 Kunpeng CPU 上的性能优化，场景为 volc_operator_sim 测试库。
目标 pipeline 为：

pipeline_text_fineweb_full_min
video_scene_split_etl
pipeline_image_full_min
audio_asr_prep_canonical
pipeline_pdf_full_min
pipeline_ad_nuscenes_min

初步分析所有pipeline 有大量 UDF 调用， join / filter / groupby 等操作较少。

当前确认的优化点如下


减少UDF过程中的跨界损耗	"【背景】
使用Daft的UDF功能时，执行引擎内部存在大量跨边界的数据移动和格式转换：
1. Rust ↔ Python 边界转换：Rust中的数据类型需要转化为Python UDF能处理的对象，Python UDF的返回值需要变为Daft的内部列数据
2. UDF阶段之间的数据传递
【设计文档】
https://onebox.huawei.com/v/a56b1da55e3a5d15aea1c9efe38e66ea?type=0"
Rust重写python的UDF算子	"【标题】
Rust重写算子 （0.75/每个算子，共13个算子）
【背景】
Python解释器中只能逐行执行Python定义的处理逻辑，将产线中的常用算子下沉到Daft的原生层实现，可以批量执行、减少Python-rust边界、减少编译器调度的影响
【描述】
在Daft中，使用Rust重写产线中的常用算子，从而提升产线性能"
鲲鹏BoostKit加速库针对X264/X265转码进行了深度优化	"【背景】
产线中存在如视频预处理、转码、解码等操作，可以使用X264/X265转码可以有效降低CPU开销
【描述】
使用鲲鹏BoostKit加速库，加速视频解码、转码操作，优化产线性能"
优化结构体转换优化，提高跨界传输效率	"【背景】
使用Daft的UDF功能时，执行引擎内部存在大量跨边界的结构体移动和格式转换：
1. Rust ↔ Python 边界转换：Rust中的结构体需要转化为Python UDF能处理的对象
2. UDF阶段之间的数据传递
【描述】
优化结构体的转换小路，从而提升产线性能"
优化Daft中的UDF调度，充分利用CPU计算资源，提高产线处理性能	"【背景】
多模态产线中存在调用外部大模型、调用GPU/NPU等CPU负载较低的任务，可以优化该类任务的调度，充分利用CPU运算资源。
【描述】
优化Daft中的UDF调度，充分利用CPU计算资源，提高产线处理性能"
优化Daft中的hash计算操作	"【背景】
产线中存在如文本去重（dedup）、groupby 聚合等操作，groupby 需对每行计算哈希进行分桶，哈希计算带来 CPU 开销

【描述】
使用鲲鹏 920B ARM CRC32C 硬件指令（crc32cx）加速 groupby 行哈希计算（groups.rs:82 Crc32Hasher，DAFT_ARM_ENABLE_CRC32C_ROW_HASH 门控），优化去重聚合性能"
length SVE 谓词 cntp	"【背景】
产线中存在如文本清洗、字段长度统计等操作，需对 UTF-8 字符串逐字节解码统计字符数（col.length() → chars().count()），标量循环数据依赖、LLVM 无法自动向量化，带来 CPU 开销

【描述】
使用鲲鹏 920B SVE 谓词寄存器（p0–p15）+ cntp 指令（@256bit，单指令统计谓词真元素数，x86 无等价谓词寄存器）重做 length kernel：char_count = byte_count − 续接字节数，SVE 32B/iter cmpeq+not+cntp，加速 UTF-8 字符长度计算，优化文本处理性能"
UDF链物理融合	"【背景】
逻辑计划拆分 UDF 后，连续 UDF 表达式可能形成多个相邻 UDFProject。每个节点都会引入独立的物理算子边界，可能产生额外的：
1. Ray actor/task 调度；
2. 中间 MicroPartition 创建与传递；
3. passthrough 列投影；
4. 节点级 metrics 和状态管理；
5. 中间结果物化或序列化。
【描述】
当父子 UDF 的并发、资源、批大小、错误处理等属性兼容时，可以把父 UDF 对子 UDF 输出列的引用替换为嵌套表达式，并生成单个物理 UDF 节点。这样保留表达式语义，同时移除一个调度和中间物化边界。"
SVE Gather 批量取数	"【背景】
Daft 在执行 take、gather、filter 后重排、join 后行选择等操作时，需要根据索引从数组中取出对应元素。原始逻辑通常按标量方式逐个读取和写入，访问模式比较离散，容易受到内存访问延迟影响。920B 所在 ARM 平台具备向量化能力，如果 CPU 支持 SVE，可以用更宽的向量指令批量处理索引和数据搬运。
【描述】
在 Daft 的 take/gather 路径中增加 aarch64/SVE 条件分支。对符合条件的 primitive 数组，在 ARM SVE 可用时使用向量化 gather 方式批量取数；不满足条件时继续走原来的通用实现。这个优化主要降低行选择、重排、过滤后收集数据时的循环开销和访存等待，对 image、text、join、dedup 等存在大量 take/gather 的产线有潜在收益。"
文本字节长度 Offset 快路径	"【背景】
文本类产线中经常需要计算字符串长度，例如过滤过短文本、统计文本字段大小、清洗异常样本、判断 caption/prompt 长度等。Daft 原始的字符串长度计算路径偏通用，会逐行处理字符串数据。对于 UTF-8 文本，如果目标只是计算字节长度，可以直接利用 Arrow 字符串数组的 offset 信息得到长度，而不需要逐条读取字符串内容。
【描述】
在 Daft 的 UTF-8 length_bytes 函数中增加快速路径：当计算字符串字节长度时，直接通过相邻 offset 相减得到每行字符串的 byte length。这样可以避免逐行访问字符串内容，减少 Python/Rust 侧上层逻辑和字符串扫描开销。该优化对 FineWeb 清洗、文本向量化前处理、图文 caption 过滤、PDF 文本清洗等文本长度判断较多的产线更有帮助。"
ARM CRC 哈希加速	"【背景】
在 Daft 执行 hash、去重、join、group by 等操作时，会频繁对列数据计算哈希值。文本去重、MinHash 去重、anti join、部分清洗产线里都会触发这类 hash 计算。原始逻辑通常走通用 hash 算法，例如 xxHash、MurmurHash 等，兼容性好，但没有充分利用 920B 这类 ARM 服务器 CPU 上的硬件 CRC 指令能力。
【描述】
在 Daft 的 hash 内核中增加 aarch64 专用 CRC32C 快路径。当运行在 ARM 且 CPU 支持 CRC 指令时，对 primitive、binary、utf8、boolean 等常见数据类型使用 ARM CRC32C 指令计算 hash；如果不支持或类型不匹配，则自动回退原始 Daft hash 逻辑。这个优化主要减少 hash 计算中的 CPU 指令开销，对去重、join、anti join、文本清洗等 hash 密集型产线更有帮助。"
