## 功能设计说明书定位和写作说明

系统功能是对设计问题的概括和抽象，描述了系统为了完成预期输出，需要执行的某个任务、动作或活动。
功能域是对不同的功能项进行归纳和组合，对应于功能树上的某层目录。
产品可以按需选择基于某个功能域，对一组归纳和组合后的系统功能进行设计，亦可单独针对某个系统功能进行设计。
本模板描述的是基于功能域的设计方式，针对单个功能项的设计可以直接参考“功能实现设计”章节的要求写作，不需要写作功能域相关的章节。

功能设计说明书定位：
1. 对系统功能进行实现设计，建立系统功能与系统元素（通常是逻辑元素）的关系。
2. 将系统需求（SR）分配到系统元素，形成分配需求（AR）

## 其他shuoming

文档目的是实现 Daft 在 Kunpeng CPU 上的性能优化，场景为 volc_operator_sim 测试库。
目标 pipeline 为：

pipeline_text_fineweb_full_min
video_scene_split_etl
pipeline_image_full_min
audio_asr_prep_canonical
pipeline_pdf_full_min
pipeline_ad_nuscenes_min

初步分析所有pipeline 有大量 UDF 调用， join / filter / groupby 等操作较少。

当前确认的优化点如下：

### 1. 减少 UDF 过程中的跨界损耗

**背景**：Daft UDF 执行引擎内部存在大量跨边界的数据移动和格式转换：
- Rust ↔ Python 边界转换：Rust 数据类型 → Python UDF 可处理对象，返回值 → Daft 内部列数据
- UDF 阶段之间的数据传递开销

**描述**：优化跨语言边界的序列化/反序列化路径，减少不必要的格式转换和数据拷贝。





### 2. Rust 重写 Python UDF 算子

**背景**：Python 解释器逐行执行 UDF 逻辑，无法利用批量处理和编译器优化。将常用算子下沉到 Daft 原生层（Rust），可批量执行、消除 Python↔Rust 边界、减少 GIL 和调度开销。

**描述**：在 Daft 中使用 Rust 重写产线中的 13 个常用算子（预估 0.75 人天/算子）。

### 3. 鲲鹏 BoostKit 加速库（X264/X265 转码）

**背景**：产线中存在视频预处理、转码、解码等操作，X264/X265 转码可以显著降低 CPU 开销。

**描述**：集成鲲鹏 BoostKit 加速库，利用硬件加速视频解码/转码操作。

### 4. 优化结构体转换，提高跨界传输效率

**背景**：Daft UDF 执行引擎内部存在大量结构体跨边界移动和格式转换：
- Rust 结构体 → Python UDF 可处理对象
- UDF 阶段之间的数据传递

**描述**：优化结构体转换路径，降低序列化开销，提升产线性能。

### 5. 优化 Daft UDF 调度，充分利用 CPU 计算资源

**背景**：多模态产线中调用外部大模型、GPU/NPU 等场景下 CPU 负载较低，可通过调度优化充分利用空闲 CPU 资源。

**描述**：优化 Daft 中 UDF 调度策略，在等待 I/O 或外部服务时释放 CPU 给其他任务，提高整体产线处理性能。

### 6. Hash 计算优化（鲲鹏 CRC32C 指令加速）

**背景**：产线中存在文本去重（dedup）、groupby 聚合等操作，groupby 需对每行计算哈希进行分桶，哈希计算带来显著的 CPU 开销。

**描述**：使用鲲鹏 920B ARM CRC32C 硬件指令（`crc32cx`）加速 groupby 行哈希计算。涉及模块：`groups.rs:82` `Crc32Hasher`，通过 `DAFT_ARM_ENABLE_CRC32C_ROW_HASH` 门控启用。

### 7. UTF-8 长度计算 SVE 向量化

**背景**：文本清洗、字段长度统计等操作需对 UTF-8 字符串逐字节解码统计字符数（`col.length()` → `chars().count()`），标量循环存在数据依赖，LLVM 无法自动向量化，造成 CPU 开销。

**描述**：使用鲲鹏 920B SVE 谓词寄存器（p0–p15）+ `cntp` 指令重做 length kernel。方法：`char_count = byte_count − 续接字节数`，SVE 32B/iter `cmpeq + not + cntp` 并行统计。x86 无可编程谓词寄存器，此优化为 ARM 独占。

### 8. UDF 链物理融合

**背景**：逻辑计划拆分 UDF 后，连续 UDF 表达式可能形成多个相邻 UDFProject 节点。每个节点引入独立边界，带来额外开销：
1. Ray actor/task 调度
2. 中间 MicroPartition 创建与传递
3. passthrough 列投影
4. 节点级 metrics 和状态管理
5. 中间结果物化或序列化

**描述**：当父子 UDF 的并发、资源、批大小、错误处理等属性兼容时，将父 UDF 对子 UDF 输出列的引用替换为嵌套表达式，生成单个物理 UDF 节点，移除一个调度和中间物化边界。

### 9. SVE Gather 批量取数

**背景**：Daft 在执行 take、gather、filter 后重排、join 后行选择等操作时，需根据索引从数组中取元素。原始逻辑按标量逐个读取写入，访问模式离散，受内存延迟影响。

**描述**：在 Daft 的 take/gather 路径中增加 aarch64/SVE 条件分支。对符合条件的 primitive 数组，在 ARM SVE 可用时使用向量化 gather 批量取数；不满足条件时回退通用实现。主要降低行选择、重排、过滤后收集数据时的循环开销和访存等待。

### 10. 文本字节长度 Offset 快路径

**背景**：文本产线中频繁计算字符串长度（过滤过短文本、统计字段大小、清洗异常样本、判断 caption/prompt 长度等）。原始字符串长度计算路径偏通用，逐行处理字符串数据。

**描述**：在 Daft 的 UTF-8 `length_bytes` 函数中增加快速路径：直接通过 Arrow 字符串数组相邻 offset 相减得到每行 byte length，避免逐行访问字符串内容。对 FineWeb 清洗、文本向量化前处理、图文 caption 过滤、PDF 文本清洗等场景有直接收益。

### 11. ARM CRC 哈希加速

**背景**：Daft 执行 hash、去重、join、group by 等操作时频繁计算哈希值。原始逻辑走通用 hash 算法（xxHash、MurmurHash），未利用 920B ARM 服务器 CPU 的硬件 CRC 指令。

**描述**：在 Daft 的 hash 内核中增加 aarch64 专用 CRC32C 快路径。当运行在 ARM 且 CPU 支持 CRC 指令时，对 primitive、binary、utf8、boolean 等常见数据类型使用 ARM CRC32C 指令计算 hash；不支持或类型不匹配时回退原始 Daft hash 逻辑。
