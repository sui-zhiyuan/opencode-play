# 需求分析概述

【关键内容】对版本初始需求包中的所有需求进行初步分类、给出分析策略和文档要求：
【输入】：IR清单
【处理】：
1. 版本SE对需求进行分类、给出分析策略。
    - 明确哪些是功能性需求，哪些是非功能性需求，并确定采用哪个章节的模板的（以便参考模板中的分析指导）；
    - 哪些需求比较重要、需求间影响复杂，且前期IR分析不充分，还要做业务场景分析
    - 哪些需求设计比较复杂，需要做usecase分析
    - 哪些需求跨多个功能域交互、或者外部交互复杂，还需要做IR需求分析
    - 哪些需求比较简单，可以免分析，直接输出SR
2. 需求分析概述和文档计划，并决定功能性需求如何进行输出，可以根据需求聚类情况，拆分成多篇文档；例如同一类需求可能放在一篇文档内一起分析。
3. 非功能性需求单独一篇文档输出或按类别分成多篇文档输出。文档中只写作包需求中涉及到的DFX属性，其他DFX属性直接删除或者写NA。

【输出】：
各需求的输出文档要求

【参考】功能性需求、非功能性需求的划分讨论：
二者的分析方法，从根本上都是基于场景和用例分析，本身没有大的差异。有的需求从客户角度看兼有两种属性，例如HA的双机备份，在网络层是DFX需求，但在网元层是功能。
这里的只讨论一个需求是放在“功能性需求”章节写，还是放在“非功能性需求”章节写。一个参考建议：

1. 涉及的功能或架构元素相对清晰、简单的，偏业务行为类的需求，放在“功能性需求”章节，基于usecase分析
2. 涉及整机系统、众多功能或架构元素的、机制/属性类的需求，放在“非功能性需求”章节分析。“非功能性需求”部分的每个章节，往往有不同的分析方法、历史经验总结的基线要求等。例如：
    - 新单板、硬件、整机需求（当前光/数通走IR需求）

需要说明的是，本节的工作本应该在CDT阶段完成。但考虑到实际操作中有遗漏或质量不满足要求的情况，本节的活动实际上是前阶段活动的迭代和补位。需要尽可能减少遗留到本节的分析内容。

【输入】：结构化IR、场景库、特性列表（可选）
【处理】：
1. 分析需求的使用场景，例如业务部署安装场景、运行场景、操作维护场景等，以及为什么(Why)要实现这个需求，准备在什么场合（Where）用来解决什么样的问题（what）；

## 场景分析

【关键内容】
主要展开该需求/需求组相关的场景，可能是运行场景，也可能是操作、维护、制造等生命周期场景
对部分比较重要、需求间影响复杂，且前期分析不充分的IR需求，进行场景分析，澄清需求信息。
兼容性分析/差异分析：描述此场景可能影响到的以前版本的功能行为，外部界面，或者相关的外部协议等因素。是否能够兼容以前的版本，是否能够宽进严出，指出哪些地方可能产生不兼容的情况。

【业务场景分析】
组网场景分析，要尽可能全面的分析各种可能应用的场景，明确分析了哪些，那些可以支持，哪些不能支持，以便于各领域对齐，并站在客户角度进行有效的风险决策。
组网+业务场景分类的原则(供参考)：以组网为主线划分场景，一个组网作为一个场景，不同业务流在场景中独立描述
Tips: 实际场景的组织以业务,还是以组网,主要是尽量减少冗余信息描述,考虑差异性,共性大的放在高级节点.
如果不同的场景维度对需求方案的影响存在耦合，即某个处理逻辑在不同组合场景下是不同的，需要对目标场景进行组合分析。

【操作场景分析】
逐个描述需要分析操作场景，对于增强型系统，这里仅需描述增强或新增部分。在这部分场景中主要描述人机交互、机机交互场景，并按照UCD方法进行场景分析。通过操作场景推导可维护性需求、可测试性需求、网管需求。
 重点描述系统和相关用户角色的接口与交互，主要操作步骤，相关条件和约束，异常情况处理等。对于增强型系统，这里仅需描述增强或新增部分。下面的事例是一个比较全面的场景分析描述，具体写作的时候，并不一定要严格按照下面的详细程度来描述，比如后面的顺序图，只需要在操作比较复杂的情况下使用。
应该描述用户在场景中的各个节点的配置过程都要描述出来，需要给出实际的命令行设计，并且要求给出各个点的Buildrun。同时，配置过程需要包含CLI的配置过程，MIB的配置过程，V8还需要包含Netconf的配置过程。另外，还需要考虑该特性将来可能面对的不是全新开局，因此，需要对一些典型场景描述在一个已有环境中添加部署该特性的升级过程。
【维护场景分析】
1）业务故障定位：描述该特性在网络上应用时可能出现的故障，进而描述需要实现哪些可维护性需求才能方便问题的定位，由于这篇文档不描述具体的实现方法，因此可维护性需求主要从信息的完备性考虑，不涉及到具体怎么实现。例如设计需要要求我们的系统能够在1分钟之内启动，等到最终实现的时候，如果达不到这个需求，我们一定要优化，优化之前一定要搞清楚各个阶段的时间消耗以找出性能瓶颈，而这个就应该在我们的系统需求中增加统计各个阶段启动消耗时间的项目，以达到可维护的目的；
2）业务统计：针对这个特性，应该提供什么样的统计信息才能对业务开展情况进行分析；
首先，需要描述如何向用户展现业务运行是否正常，最主要的就是基于业务的Display命令，以及我们的MIB表的定义。
在故障这边，需要对业务相关外在故障模型进行描述，比如配置错误，协议邻居Down，不同厂商互通问题等等此类用户可以感知的故障，需要描述这些故障是如何展现给用户的（例如告警），如何定位（例如Display，Debug，日志，网管展现等等），以及如何进行业务恢复。

## X1需求

### X1用例分析（含编写建议的模板，根据需要选用）

【关键内容】
本节描述IR需求的用例分析，用于导出系统功能需求（SR）。
1. 首先确认该IR关联的场景，以及该场景下涉及哪些用例。
2. 进一步把用例再打开，看该用例涉及哪些功能，以及这些功能要支撑这个用例，需要新增功能、还是修改功能。
    - 对于简单的用例，如果涉及功能较少，可以直接分析对功能影响。
    - 对于复杂的用例，如果涉及功能较多，建议采用活动图进行分析，每一个活动对应一个功能，由此得出该用例涉及的功能。
3. 为每个涉及的功能生成SR。SR是功能变更信息的载体，一个SR关联到一个功能，一个功能的变更可以用多个SR承载。
有可能多个相关联的IR一起在一个用例里分析，最终导出完整的功能需求即可。也可能一个需求会需要多个用例来进行分析，或者这几个用例属于不同的业务场景。
为每个用例定义一个好名字非常重要，如果找不到合适的名字，则意味者此用例的目标不清晰。使用动词+名词的方式命名每一个用例，这个动名词的短语必须能够清晰的表达出此用例的主执行者的目标。完整并且清晰的目标的特征如下：
1. 它明显和一个主执行者密切相关，而且只和一个主执行者密切相关。
2. 它对主执行者和其它相关人员是有价值的。
3. 它与你当前正在写作的目标层次一致。如果不一致，则需要重新思考这个用例，或将它移动到合适的层次中。
用例的这一个目标必须是主执行者的目标。执行者是与系统具有任何行为的事物。执行者可能是一个人，一个公司或组织、一个程序或计算机系统、一个其他功能或本功能自身。主执行者是通过用例达到了目标的执行者。
主执行者是通过用例达到了目标的执行者。
特别的，待开发系统和它的子系统也可以作为用例的一个执行者，但不能作为主执行者。只有外部的执行者才能作为主执行者并通过用例实现自身的目标。例如“记录日志”用例，在此用例隐含的主语是“系统”，但不能据此认为此用例完成了“系统”的目标。虽然没有出现“管理员”这几个字，但此动作确实完成了“管理员”这个主执行者的目标。即在用例中，系统可以有动作，但不能有目标，所有的目标必须是外部主执行者的。即用例只能100%从系统外部的角度考虑，描述系统或系统内部行为的目的只能是为了实现某个外部主执行者的目标。
与用例的目标类似，用例中每个动作都必须具有目标，而且必须是某个外部主执行者的目标。凡是没有外部主执行者认领的场景或动作，都不应该在用例中出现。不过，我们必须为每个用例的目标命名，即为每个功能需求取名，但没有必要为用例中的每个动作命名。
用例必须全部达到下面的判定标准：
1. 所有的主执行者和目标都已经被识别并写出；
2. 客户或其代表认为没有遗漏用例，并且每个用例都是正确并且可读的；
3. 系统设计人员认为能够实现这些用例。
4. 系统测试人员认为能够验证这些用例。

本章节描述此用例的概要

【Actor】
本章节描述此用例涉及的所有Actor（执行者）。

【前置条件】
在没有“前置条件”的情况下，应该写“前置条件：无”。
用例的前置条件声明了启动该用例之前系统必须满足的条件。
一个常见的例子是“用户已经通过了身份验证”。通常，前置条件是其他用例的执行结果，“用户已经通过了身份验证”这个前提条件是“验证用户身份”用例执行成功后的结果。

【最小保证】
在没有“最小保证”的情况下，应该写“最小保证：无”。
最小保证是在主执行者的目标不能被满足的情况下，对系统的最低要求，例如系统数据不能丢失，业务不能中断等。
每一个失败条件和处理方案都会在用例的某个扩展场景中进行描述。此处需要描述的是所有场景都必须做到的要求。

【成功保证（后置条件）】
在没有“成功保证”的情况下，应该写“成功保证：无”。
成功保证是在主执行者的目标被满足的情况下，系统的输出和达到的状态。


【触发事件】
在项目组约定将“触发事件”写作为用例主成功场景第一步的情况下，此节可删除。
用例的“触发事件”不能为“空”，也不能为“无”。
触发事件是启动用例的事件，紧接着就发生用例的第一步。
触发事件必须能够被系统检测到，“客户决定使用系统”不是一个恰当的触发事件。

【主成功场景（基本事件流）】
本节内容必选。
一系列的成功动作最终实现了主执行者的目标，并保护了项目相关人员的利益，它们构成了用例的主成功场景。主成功场景应简短明了，指明了系统提供的服务。
主成功场景能完成本用例的目标，未必是达到目标的最短路径，但必须是最常发生或用户最喜欢发生的路径；其他成功场景、所有错误处理，在扩展场景中描述。
用例中的每个场景、场景中的每个动作都必须具有外部主执行者的目标。
主成功场景用带编号的步骤进行描述。每个步骤粒度相近，其目标层次低于整个场景的目标层次。任何情况下，每个步骤都不得省略主语，不能使用被动语态。建议不使用复杂的句子。
步骤1。
步骤2。
……
步骤N。
主成功场景的最后一个步骤。此步骤完成后，必须达到了主执行者的目标。
场景的一次交互包含下面的4个部分：
1. 主执行者向系统发送请求和数据。
2. 系统验证收到的请求和数据。
3. 系统更改内部状态。
4. 系统向执行者返回结果。
作者可以把上面的每个部分写成一个单独的执行步骤，也可以用不同的方式合并其中的几个部分，或者将4个部分合并成一个执行步骤。
合并的原则取决于每个部分的复杂程度和执行过程中在什么地方会发生扩展场景来决定，不存在对所有用例通用的写作方式。
使用下面的2种方式之一表达重复的步骤：
1. 在单个步骤中直接表达，如：“主执行者执行XX动作，直到满足YY条件时停止”。或“此步骤操作可能会重复多次”
2. 在重复的步骤前表达，如：“步骤3—5可以重复执行”这句话放在步骤2之后，步骤3之前，没有编号。

【功能图 （可选）】

依据上述的主成功场景和扩展场景，识别系统功能，并建立和其它系统功能之间的关系，采用功能图形式表述系统功能之间关系。

【扩展场景】

本节包含描述多个扩展场景，包括其他成功场景和失败场景。
扩展场景指的是，在主成功场景下，因特定条件而出现的一个或多个行为分支。应对每个分支的条件及处理分支的步骤加以描述。如果说主成功场景的目标是实现主执行者的意图（与用例目标相同），那么扩展场景的目标是在异常情况下实现主执行者的某个意图（其他的成功路径），或在不能实现主执行者意图的情况下，保证系统其他相关人的利益（失败路径）。
每个扩展场景始于一个前提条件；然后，是一个步骤序列，描述在此条件下发生了什么；最后，以完成或放弃本场景的目标为结束，即，必须回到主成功场景中，或，以失败结束。
本节内容不能为“空”。如确无扩展场景，说明需求十分简单，直接用一段话描述即可，无需采用用例格式。
每个扩展场景实质上是一个从主用例中拆分出来的小型用例，所以也拥有自己的目标、目标级别、前提条件、主干（完成了扩展目标的主成功场景）和分支（完成了扩展目标的其他路径或保证其他相关人利益的其他失败路径），并按用例的方式进行写作。
任一扩展场景，只能且必须以下面的4种方式之一结束：
1. 修改或替换主成功场景的当前步骤，然后重新开始主成功场景的当前步骤、或执行主成功场景的下一步。这种情况下，不需要说明扩展场景执行后怎么办。
2. 系统给执行者其它的选择，执行完毕后回到主成功场景的某个步骤。这种情况下，扩展场景的最后一个步骤必须是“转到步骤N”。
3. 与主成功场景不同的成功路径。这种情况下，扩展场景的最后一个步骤必须是“用例结束”。
4. 没有达到主执行者目标的异常结束。在这种情况下，扩展场景的最后一个步骤必须是“用例结束”。
每个扩展场景开始于一个编号和前提条件。此编号由3部分组成：
阿拉伯数字：表示此前提条件出现在主成功场景的第N个步骤。此处不能使用自动编号，建议由作者手工编号。
英文字母：表示在主成功场景的第N个步骤中，出现了多个扩展场景，这些扩展场景按照“a”到“z”的顺序编号。同一个步骤下出现的扩展场景不多，建议由作者手工编号。
“.”（点）：分隔此编号和前提条件。
例如：“1a.”表示主成功场景的步骤1发生的第1个扩展场景，“1b.”表示主成功场景的步骤1发生的第2个扩展场景，以此类推。
特别的，有些扩展场景可能发生在任意一个步骤中，例如“a.”表示此扩展场景发生在主成功场景的任意一个步骤中。有些扩展场景可能发生在多个步骤中，例如“2-5a.”表示此扩展场景发生在主成功场景的步骤2-5中。
针对复杂的扩展场景，可能需要进一步写作此扩展场景下面的扩展场景，这种情况下，建议在此扩展场景出现分支处理的步骤中，直接写作下层扩展场景。例如，编号“1b2a.”表示在扩展场景“1b.”的步骤2中发生的第1个更下层扩展场景，此扩展场景应写作在“1b.”的步骤2下面。比“1b2a.”更下层的扩展场景，建议不编号直接写作（使用缩进），或者独立为1个单独的子功能用例。
用一个描述系统检测到了什么的短语或句子描述扩展场景的前提条件，并且在扩展场景的前提条件后面加一个冒号(：)。主用单元或备用单元发生故障、链路故障或切换、对端设备拒绝或拆线、用户中途取消操作、被叫忙、配置数据不完整、低压或掉电等都是扩展场景常见的前提条件。
扩展场景可用一段话说清楚时，可将步骤与分支条件写在一行，例如：
2a．系统检测到XX条件：系统提示失败，退出YY操作，执行ZZ操作，……，用例结束。
扩展场景较为复杂时，将分支条件写成独立的一行，例如：
2a．系统检测到XX条件：
.1. 系统提示用户，要求输入新的XX参数。
.2. 用户输入XX参数。
包含更下层扩展场景的例子：
2a．系统检测到XX条件：
.1. 系统提示用户，要求输入新的XX参数。
.2. 用户输入XX参数。
2a2a: 系统检测到XX_1条件：
..1. 系统提示用户，要求先执行XX操作后才能输入此参数
……
..2. 用例结束
.3. 转到步骤6。
在多个扩展场景中，如果处理行为一致，则应该合并这些场景。例如：
2b．系统检测到YY条件或检测到ZZ条件：系统提示失败，……，用例结束。

（5）	现网存在被攻击案例的业务。

## 系统可靠性/可用性需求分析

说明： 本章节主要考虑需要从整体视角对系统作可靠性、可用性相关的综合分析时才需要独立呈现；通常情况下，以下的分析指导应该相应在领域分析、功能性需求分析（用例分析的扩展场景）中完成。
输入：结构化的IR、功能树、场景、系统用例
分析过程：
1、	针对可靠性相关的结构化IR，分析该IR相关的场景和系统用例，评估场景中Actor或系统的各种异常对系统业务功能的影响；当干预影响需要新增系统功能或更新系统功能可靠性属性时，更新功能树；
2、	分析系统用例相关中系统功能和周边交互中，系统功能可能发生的故障对系统用例的影响，更新或增加系统用例的异常场景描述；根据可靠性属性分析所分析出的影响应当在系统功能层面实施的措施；
3、	根据领域可靠性可用性专业需求(即通过领域可靠性可用性需求基线整理得到的SDR)、领域全量场景中可靠性可用性相关场景，分析系统功能所受到的影响，提取对已有功能的影响或新增可靠性相关功能；
4、	根据对功能的影响，分解SR；

输出：
- 结构化SR
- 结构化SR刷新
- 可靠性/可用性属性刷新（刷新功能树）

参考：本文档不涉及如何建设领域可靠性可用性SDR，该任务在产品空间的领域分析中已完成。需要注意可靠性/可用性需求分析应当分析包括客户需求（标书、业界标准）分析（避免遗漏标书、标准中隐含的可靠性诉求）、公司内部标准要求分析（通常已建设包含在SDR中）、友商分析和业务异常场景识别分析等内容。参考《产品领域可信实施策略》中的可靠性能力模型，通常将各种分析结果进行分类划归到不同的可靠性功能中，以便于在后期系统设计、功能设计中进行专项分析和设计

【客户需求分析】
包含客户的标书分析和标书中提到的标准分析，将标书、标准的要求内容作为产品的设计需求之一，例如某标书对可靠性/可用性的部分内容如下：
F-10 (R) 无单点硬件故障引起服务损失
F-11 (R) 无单点软件故障或命令（Command）及命令序列引起服务损失，且不可以有单点SW故障或命令（Command）及命令序列导致网元进入某种状态，要从此状态中恢复会引起服务损失。
F-12 (O) 供应商在软件和硬件设计中，应尽力考虑人因差错的设计来减少操作维护出现故障的几率。
F-13 (I) 供应商应提供符合Telcordia SR-TSY-000385网元的可靠性块状结构图(Reliability block diagram), 说明可靠性架构，并提供基于Telcordia SR-332规范计算出的可靠性指标，以及系统主要功能的故障模式。

【公司内部标准分析】
公司内部的标准要求主要是指《可靠性（DFR）质量属性标准》、《R59标准》、《可靠性设计基线》，内部规范要求以及《产品领域可信实施策略》关键可信需求，需要分析产品本版本考虑设计和实现的相关内容，具体内容可参考发布的标准、规范、基线。

【友商分析】
大多数情况下，可靠性/可用性的友商分析会在日常进行，并将有价值的需求合入到可靠性/可用性设计基线中，这里主要描述友商宣传的有竞争力的可靠性/可用性能力。
